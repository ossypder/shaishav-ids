What is an IDS?

An Intrusion Detection System watches traffic or system logs for signs of malicious activity, and raises alerts so a human analyst can respond. Unlike a firewall, an IDS does not block traffic by itself — it observes and reports. An IDS that also blocks is called an IPS (Intrusion Prevention System).

The two classic detection approaches are:

  • Signature-based — match traffic against known-bad patterns (fast, explainable, misses brand-new attacks). This system uses this approach.
  • Anomaly-based — learn what "normal" looks like and flag deviations (catches novel attacks, but needs training data and false-positives more).

  1. Traffic Generator (backend/traffic.py) simulates benign users (browsing, logging in) and attacker IPs running scans, brute-force, SQL-injection and floods. Every observation becomes one flat event record.
  2. Recent Events (backend/rules.py) — activity from the last 4 seconds forms the window the counting rules evaluate over.
  3. Detection Rules (backend/rules.py) run threshold checks / pattern matching over that window. 4 rules: Port Scan, Brute Force, SQL Injection, HTTP Flood.
  4. Alert Log — each detection becomes an alert: rule, severity, source IP, human-readable detail.
  5. Dashboard — this page, which polls the REST API and renders everything.
Observation sources

The detection engine never changes — it always runs the same four signature rules over the last 4 seconds of events. What changes is where the events come from:

  • Simulated — backend/traffic.py generates benign users plus attacker bursts (scans, brute-force, SQL-injection, floods). Deterministic, safe, and every alert is a seeded, explainable demo.
  • Live capture — backend/capture.py sniffs real packets with scapy, one capture handle per real network interface (pcap-style, as Wireshark's dumpcap does). TCP SYNs become port_probe events and plaintext HTTP requests become http_request events, so Port Scan, DoS and SQL Injection fire on real traffic. Capture needs privileges — start the stack with ./run.sh capture.

Live-capture limitations: HTTPS payload is encrypted (no SQL-injection inspection on TLS), password attempts are likewise invisible so Brute Force stays simulated-only, and IPv6 is not parsed yet. A pseudo-interface that cannot open reports the exact OS error in the status chip.

Example: spotting SQL injection

A request like /products?id=1' OR 1=1-- is not a normal page — it is a SQL fragment that would make a vulnerable database return every row. The rule simply checks whether a request URL contains a known fragment (' OR 1=1, UNION SELECT, …) and, if so, raises a Critical alert naming the source IP.

Design decisions
  • Rule-based, not ML — every alert is traceable to an explicit rule and threshold, which makes the system explainable and easy to evaluate in a report.
  • Thresholds in one config block — RULE_CONFIG in rules.py, easy to tune and to discuss sensitivity vs. false positives.
  • Alert deduplication (cooldown) — one alert per (rule, source IP) burst; repeats are suppressed for 30 s so one attack = one alert, mirroring real IDS aggressor logging.
  • In-memory state, no database — keeps the MVP self-contained; persistence is listed under future work.
  • Two observation sources, one engine — the synthetic generator keeps the demo safe and reproducible; its event record is the exact shape capture.py produces from real packets, so the rules run unchanged over both.
  • REST API (FastAPI) — POST /simulate, GET /events, GET /alerts, GET /rules, GET /stats, POST /reset. Interactive docs at /docs.
Limitations & future work
  • Live capture exists (scapy), but encrypted protocols are opaque to signature matching; a next step is reading server/auth logs for Brute Force on real systems.
  • No persistence — alerts vanish on restart; next step: SQLite/Grafana dashboards.
  • Detection only — no blocking; next step: convert to an IPS by adding firewall rules.
  • No ML — next step: a supervised model (e.g. Random Forest on NSL-KDD) compared against the rules for accuracy/F1.
